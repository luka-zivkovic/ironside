# Worker Scheduler v1 (M6-05)

Status: implemented. Owner: `apps/worker/src/scheduler.ts`, `packages/db/src/{export-configs,otlp-forward-rules,webhooks}.ts` (claim functions), `packages/db/migrations/0001_baseline.sql`.

## Purpose

Closes the "tested, callable function only, no scheduler" gap tracked across M5's importers and M6's exports/forwards/webhooks specs — `runExport`, `forwardOtlpTraces`, and `runWebhooks` were fully built and tested but nothing ever called them automatically. This batch wires the three subsystems that already had a per-row config table with an `enabled` flag, plus `runRetention` (a global sweep with no per-row target).

**LangFuse/LangSmith import scheduling is explicitly out of scope for this batch** — unlike exports/forwards/webhooks, there is no persisted credentials/config table for those importers at all (verified by reading every migration; `import_checkpoints` is runtime progress state, not source configuration). Building that table, its CRUD routes, and its scheduling is a separate, larger batch.

## Design

- **Claiming, not a second BullMQ queue.** The Postgres baseline defines `poll_interval_seconds` (per-row override, sane per-subsystem defaults: exports 1h, forwards 5m, webhooks 1m) and `next_run_at` (defaults to `now()`, so a newly-created rule is due on the very next tick) on `export_configs`, `otlp_forward_rules`, and `webhook_rules`. `claimDueExportConfigs`/`claimDueOtlpForwardRules`/`claimDueWebhookRules` (`packages/db/src/*.ts`) atomically claim every due, enabled row via `UPDATE ... WHERE id IN (SELECT ... FOR UPDATE SKIP LOCKED) RETURNING *`, advancing `next_run_at` to `now() + poll_interval_seconds` in the same statement. This is what makes concurrent ticks — or, if ever run with more than one worker replica — safe without any coordination beyond Postgres row locking; a BullMQ repeatable job would add a second queue/Redis job type for no correctness benefit, since the locking that actually matters already lives at the database layer.
- **A plain `setInterval` loop** (`apps/worker/src/scheduler.ts`'s `startScheduler`) drives four ticks: exports/forwards/webhooks on a shared, configurable `tickIntervalMs` (default 30s), retention on its own much longer `retentionIntervalMs` (default 6h — dropping ClickHouse partitions is not something to attempt every few seconds). Each fires immediately on start, not just on the first interval, so a fresh worker process doesn't wait a full tick before doing anything.
- **One failing row never stops a tick.** Each subsystem's per-row work is wrapped in its own try/catch reporting to `onError(subsystem, error)` (default: `console.error`) — the same "one bad item doesn't fail the whole batch" policy used throughout ingest. A row's `next_run_at` is already advanced by the claim itself, so a permanently-misconfigured rule (e.g. an unreachable destination) gets retried on its own interval, not hot-looped or stuck.
- **Credentials are decrypted here, not in the runners.** `decryptSecret` (moved from `apps/api/src/lib/encryption.ts` to `@ironside/shared` in this batch — a pure crypto utility with no framework dependency, needed by both the API, which encrypts on create, and now the worker, which decrypts to actually run) is called once per claimed row, matching the existing "runner takes an already-decrypted value" contract every runner already had (`destinationSecretAccessKey`, `destinationAuthHeader`, `signingSecret`).

## SSRF guard is live on the scheduler path

`forwardOtlpTraces`/`runWebhooks` already validate customer-supplied destination URLs (the `forwardOtlpTraces` side fixed in M6-04, immediately prior to this batch); the scheduler calls both without `allowPrivateDestinations`, so a rule pointing at a private/loopback address fails with a clear per-row error and does not send anything — verified with a real integration test asserting both subsystems reject `http://127.0.0.1:9/...` and that `next_run_at` still advances (no hot-loop retry of an obviously-broken rule).

## Verification

- `packages/db/test/scheduling.test.ts`: 8 tests — due/not-due/disabled row selection, `next_run_at` reschedule accuracy (asserted against the row's own `pollIntervalSeconds`, not a hardcoded default), and concurrent-claim exclusivity (`Promise.all` of two claim calls against the same due row — exactly one wins, via `FOR UPDATE SKIP LOCKED`), spot-checked once each for OTLP forwards and webhooks to confirm the pattern was applied consistently.
- `packages/shared/test/encryption.test.ts`: round-trip, random-IV non-determinism, AEAD tamper detection, malformed-prefix rejection, missing-secret-env rejection (moved+retested, not just moved).
- `apps/worker/test/scheduler.test.ts`: 6 end-to-end integration tests against the real local stack — a claimed export config actually runs (real ClickHouse → real DuckDB → real MinIO, same pipeline `export-runner.test.ts` proves in isolation) and records `lastRunStatus: "success"` with the correct row count; an export whose filter matches zero traces records `rowCount: 0`, not `null`; a claimed export with bad credentials records `lastRunStatus: "error"` without crashing the scheduler; a row whose credentials fail to decrypt is reported via `onError` without blocking other due rows in the same tick; a claimed forward rule and webhook rule both get claimed (proven via `next_run_at` advancing) when targeting a private destination — SSRF rejection itself is proven at the unit level by `otlp-forwarder.test.ts`/`webhook-runner.test.ts`, not re-asserted here (see below); `stop()` actually halts further ticks.
- Manually started the real worker process against the live local stack and confirmed clean startup ("ironside-worker: scheduler running", no errors) with zero configured rules — correctly a no-op tick, not a crash on an empty claim set.

### Two bugs caught by code review, fixed and regression-tested

1. **The scheduler double-recorded a successful export's outcome, corrupting the empty-result case.** `runExport` already records its own outcome on every path it reaches (empty-result success with `rowCount: 0`, non-empty success, upload failure) — the scheduler's `tickExports` called `recordExportRun` a *second* time on success, and for an empty-result export, `outcome.rowCount ?? null` overwrote the correctly-recorded `0` back to `null`. Fixed by removing the scheduler's own success-path recording (its error-path recording is still needed, since a failure before `runExport` reaches any of its own recording calls — e.g. `decryptSecret` throwing — would otherwise have no bookkeeping at all). Regression-tested: reverted the fix and confirmed the exact `rowCount: null` failure signature reproduces.
2. **`claimDueOtlpForwardRules`/`claimDueWebhookRules` claim across the WHOLE database, not scoped to any one project** — correct scheduler behavior (a real scheduler polls every project), but it made the SSRF-rejection test flaky under full-suite parallel execution: other test files' leftover enabled rows in the shared local Postgres instance (e.g. `packages/db/test/webhooks.test.ts`'s fixture, whose `signingSecretEncrypted: "unused-in-this-test"` is a deliberately-not-real-ciphertext string) got claimed in the same tick and threw a *different* error (`decryptSecret` failing on a non-ciphertext string) than the test was asserting on, since `onError`'s error wasn't correlated to a specific rule id. Root-caused empirically (temporary debug logging on a claimed-rows dump, not guessed) after first suspecting — and ruling out, by testing directly — `IRONSIDE_ENCRYPTION_SECRET` cross-file `process.env` pollution and vitest's default test-file parallelism (same general class of shared-test-database issue noted in `ROADMAP.md`'s M7-04 retention-test flake, root-caused there via `--no-file-parallelism`). Fixed by scoping the test's own assertions to its own rule ids (`next_run_at` advancing, proving claim + evaluation) rather than asserting on "the first error of this subsystem" from a shared `errors[]` array that can contain unrelated rows' failures. Not a scheduler code bug — the scheduler's global-claim behavior is correct — purely a test isolation fix.
