# Rate limiting, quotas, and retention v1 (M7-03)

Status: implemented — rate limiting live on every ingest route, per-project quota overrides settable via API, retention job built and tested; scheduler wiring since added in M6-05 (runs on its own 6h-default interval).

## Rate limiting

`apps/api/src/middleware/rate-limit.ts` — a fixed-window per-project limiter backed by the same shared Redis instance every route already gets via `machineAuth`, not a separate connection or an in-memory-per-process counter. Redis keeps limiter state consistent across horizontally scaled API instances (`INCR` + `EXPIRE`, one key per `(projectId, window)`) and avoids losing all counters on a single process restart.

Applied to machine write paths — native `/api/v1/ingest`, OTLP `/v1/otel/traces`, LangFuse-compatible `/api/public/ingestion` and `/api/public/scores`, plus `/api/v1/media` — mounted after `machineAuth` on each. They share one project write budget. Owner-session query and management routes are not rate limited by this ingest quota.

Fixed-window (not sliding-window/token-bucket) is a deliberate simplicity choice — it allows up to 2x the limit across a window boundary in the worst case, an acceptable trade for a self-hosted product where this exists to catch a runaway client, not to bill per-request.

## Per-project quota overrides

`projects.rate_limit_per_minute` and `projects.retention_days` — both nullable integers, `null` meaning "use the platform default" (`DEFAULT_RATE_LIMIT_PER_MINUTE`/retention default env vars), not a magic sentinel value. Settable via `PATCH /api/v1/projects/:id/quotas`, restricted to the caller's own organization (same authorization boundary as the rest of `/api/v1/projects`).

A field is only changed when the request body actually includes it — an omitted field is left untouched, while an explicit `null` clears the override back to the platform default. This distinction needed care at three separate layers, and each one had a real bug caught and fixed before merge:
- **SQL**: `packages/db/src/projects.ts`'s `setProjectQuotas` builds its `UPDATE ... SET` clause dynamically, only including a column when the caller's input object actually has that key (`"rateLimitPerMinute" in quotas`), rather than `COALESCE($n, existing_column)` — verified the naive `COALESCE` approach genuinely fails by temporarily reverting to it: it turned out unable to ever clear a quota back to `null` at all (`COALESCE(null, existing)` always falls back to the existing value), confirmed by the regression test failing exactly as expected before the fix was restored.
- **TypeScript**: `exactOptionalPropertyTypes: true` (already enabled repo-wide) caught that Zod's `.optional()` types an omitted field as `undefined`-valued, not genuinely absent — spreading the parsed request body directly into `setProjectQuotas` would have passed an explicit `rateLimitPerMinute: undefined`, defeating the "only touch provided fields" contract at the type level (not just conceptually). Fixed in `apps/api/src/routes/projects.ts` by explicitly checking key presence (`"rateLimitPerMinute" in parsed.data`) before including it.
- **Wire contract**: `packages/shared/src/management.ts`'s `updateProjectQuotasRequestSchema` uses `.nullable().optional()` on both fields so the same three-way distinction (provide a value / provide null / omit) survives across the HTTP boundary.

The rate limiter's own read path caches a project's override in Redis (`quota:ratelimit:<projectId>`, 60s TTL) — the limiter runs on every single ingest request, so a Postgres round trip per request was unacceptable; a stale cache entry means a quota change takes up to a minute to take effect, which is fine for a quota control (unlike machine-credential revocation, which must be immediate for security reasons — see spec/project-key-management-v1.md).

## Retention job

`packages/clickhouse/src/retention.ts` (`listPartitions`, `dropPartitionsOlderThan`, `markProjectDataDeletedOlderThan`) + `apps/worker/src/retention/retention-runner.ts` (`runRetention`), following the same "callable function + tests only, scheduler wiring is a follow-up" pattern M5's importers and M6's exports/forwards/webhooks all shipped with.

**The core design constraint, discovered by reading the actual schema before writing any code**: `traces`/`observations`/`scores` partition by `toYYYYMM(timestamp)` — a calendar-month partition, NOT per-project. A single partition holds every project's rows for that month. This means `ALTER TABLE ... DROP PARTITION` — the literal mechanism the DoD names ("drop CH partitions") — can only enforce ONE global cutoff across the whole platform, not a per-project one; dropping a partition drops it for every project sharing that month.

The runner reconciles this with per-project overrides in two tiers:
1. **Global partition drop** — computed at the LOOSEST retention window in effect (`max(platform default, every project's retentionDays override)`), since dropping a partition that still holds ANY project's still-in-window data would violate that project's retention promise. This is the primary, cheap mechanism (`ALTER ... DROP PARTITION` is a metadata operation, not a scan).
2. **Row-level deletion** — only for projects with an *explicit* override *shorter* than that global floor, via `markProjectDataDeletedOlderThan`. This is heavier (an `INSERT ... SELECT` mutation using the same ReplacingMergeTree re-insert pattern as every other write in this codebase, not an in-place `ALTER ... DELETE`) but the only way to target one project's data without touching its partition-mates.

**A real performance bug caught during testing, not in code review**: an earlier version of tier 2 applied to every project whose *effective* retention (including the platform default) was below the global floor — which is correct in the strict sense (a default-retention project genuinely does have data older than the floor once some other project's long override raises it), but meant that ANY project setting a long retention override forced a full per-project ClickHouse mutation for EVERY OTHER project on the platform, every retention run. This was caught not by reasoning about it but by an actual test hang: `runRetention` against the real local stack (35 accumulated test projects, one with a stray 3000-day override left over from a crashed prior test run) never completed within a 60-second timeout. Fixed by restricting row-level deletion to only projects with an *explicit* override shorter than the floor — a default-retention project's old data still gets removed once the floor itself comes back down via a normal partition drop, with no retention-promise violation in the meantime (the platform default was never breached, only a *stricter* project's own promise would have been). Re-verified: the full 3-project test suite now completes in ~300ms instead of hanging.

**A correctness bug in `is_deleted` semantics, also caught by running against real ClickHouse, not assumed**: `ReplacingMergeTree(event_ts, is_deleted)`'s `is_deleted` column is not just an app-level soft-delete convention — it's the storage engine's own tombstone marker. `FINAL` doesn't merely dedup to the highest-`event_ts` version of a row; once that version has `is_deleted != 0`, `FINAL` excludes the row entirely. The retention test suite is written against this observed behavior (assert the row is *absent* from a `FINAL` query, not present-with-`is_deleted=1`), not an initial (wrong) assumption that `FINAL` would return the row with the flag visible.

**A real TOCTOU race flagged by code review, fixed with a grace-period safety margin**: `dropPartitionsOlderThan`'s "check the partition's actual max timestamp, then drop" is two separate ClickHouse statements with no cross-statement transaction to make them atomic. Since ingest is fully async (`apps/api/src/routes/ingest.ts` fast-ACKs to a queue; a worker inserts later) and event timestamps are client-supplied and unclamped, a row could in principle land in an old partition between the check and the drop — a backfill client sending an old-dated event, or simply a queued ingest job that hadn't drained yet — and be destroyed permanently with no error. Fixed with `PARTITION_DROP_GRACE_PERIOD_MS` (24 hours): the effective cutoff used for the drop decision is pushed back by that margin, so any realistic ingest lag has long since drained before a partition becomes droppable. This does not make the two statements atomic — it narrows the race window from "any event arriving during normal operation" to "an event arriving implausibly late (>24h after being generated)". Verified the fix genuinely discriminates: temporarily zeroed the grace period and confirmed a dedicated regression test (a trace timestamped 12h before the nominal cutoff — old enough to be wrongly dropped without the margin, but within the 24h buffer) failed as expected, before restoring the fix.

- No S3 lifecycle policy support — the DoD text names "drop CH partitions + S3 lifecycle" as the retention mechanism; this batch built the ClickHouse half only. `@ironside/storage` currently has zero lifecycle-policy support (confirmed by reading the whole module before starting: only `putJson`/`getJson`/`putFile`/`ensureBucket`/`healthCheck`/`close`), and the raw ingest event log in object storage (immutable, replayable per the original design doc) has its own retention question distinct from ClickHouse's queryable copy — worth a dedicated follow-up rather than folding in as an afterthought here.
- Rate limiting only applies at the API layer's ingest routes — there's no equivalent guard on the OTLP-forward/export/webhook egress paths (those already have their own SSRF/scope protections from M6, but no rate limiting of their own).
