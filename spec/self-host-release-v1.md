# Self-host release v1 (M7-04)

Status: implemented — full `docker compose up` stack, release image CI, docs, license. `v0.1.0` tag not cut (that's a user action).

## Scope

The last M7 DoD items: docs (README, self-hosting guide, LICENSE) and the fresh-machine test (clone → `docker compose up` → first trace in UI in <10 min; release images build in CI; tag v0.1.0). Before this batch, `docker-compose.yml` only stood up infrastructure (Postgres/ClickHouse/Redis/MinIO) — a fresh clone had no way to run the application containers themselves without a local Node toolchain, which doesn't satisfy "clone → docker compose up → trace in UI" for someone who just wants to self-host.

## Docker images

`apps/api/Dockerfile`, `apps/worker/Dockerfile`: identical multi-stage shape — a `build` stage that copies the whole monorepo (root `tsconfig.json`/`tsconfig.base.json` + `packages/` + `apps/`, needed because every package's own `tsconfig.json` extends the root one via project references), runs `pnpm install --frozen-lockfile` and `pnpm build` (which builds every workspace package `-r --sort`, in dependency order), then a `runtime` stage that does a fresh `pnpm install --frozen-lockfile --prod` (skips devDependencies, never runs `tsc`) and copies in only the built `dist/` directories from the build stage. The full source tree and devDependencies never ship in the final image.

`apps/web/Dockerfile`: same build-stage shape, but only needs `@ironside/shared` (its one workspace dependency) built alongside itself — `vite build` produces a static `dist/`, which the runtime stage serves via `nginx:1.27-alpine`. `apps/web/nginx.conf` proxies `/api/` and `/health` to the `api` service (by Docker Compose's internal DNS name) and falls back to `index.html` for any other path (SPA client-side routing). This deliberately mirrors `apps/web/vite.config.ts`'s dev-time proxy: Vite's `VITE_API_URL` env var is compile-time-baked into the static bundle, not runtime-configurable, so rather than require a self-hoster to rebuild the image with their own API host baked in, the web app's `fetch` calls stay relative paths and nginx handles the actual routing at request time — the same-origin contract the CORS/auth model already assumes holds identically in dev and in this container.

`docker-compose.yml` gained `api`, `worker`, and `web` services, wired to the existing infra services using their **container-internal** hostnames and default ports (`postgres:5432`, `clickhouse:8123`, `redis:6379`, `minio:9000`) — distinct from the **host-exposed** offset ports (`5433`, `8123` host-mapped, `6380`, `9010`) that exist so a locally-running dev toolchain and a local coeval instance can coexist without port clashes. `api`/`worker` `depends_on` every infra service with `condition: service_healthy`, so `docker compose up` won't start the application containers against a database that isn't accepting connections yet.

## The two "already idempotent" boot behaviors this batch relies on, verified rather than assumed

`apps/api/src/index.ts` and `apps/worker/src/index.ts` already call `runPgMigrations`/`runChMigrations`/`storage.ensureBucket()` on every boot (established since M0's DoD required migrations to be idempotent on re-run). This batch didn't need to add a separate migration-runner service or init container — confirmed by reading both entrypoints before writing the compose config, not assumed from the DoD text alone.

## A real bug found by actually running the fresh-machine test, not by inspection

The very first real `docker compose up` run (isolated project name, real Docker, not a mock) crashed the `api` container on boot:

```
BucketAlreadyOwnedByYou: Your previous request to create the named bucket succeeded and you already own it.
    at ... Object.ensureBucket (file:///repo/packages/storage/dist/src/index.js:21:17)
```

Root cause: `apps/api` and `apps/worker` are separate processes that each construct their own `ObjectStorage` and independently call `ensureBucket()` at boot. `docker-compose.yml`'s `depends_on: minio: condition: service_healthy` only guarantees MinIO itself is up — it says nothing about ordering between `api` and `worker`, which start concurrently. The pre-existing `ensureBucket()` (`packages/storage/src/index.ts`) did `HEAD bucket` → on failure, `CREATE bucket`, with no handling for the create itself failing because a concurrent caller's create already won: both containers' `HEAD` calls could race ahead of either's `CREATE`, so both then attempted `CREATE`, and the loser's request failed with `BucketAlreadyOwnedByYou` — a legitimate S3-compatible response meaning "this bucket exists and you already own it," not a real error, but the code re-threw it uncaught, crashing the process.

Fixed by catching `CreateBucketCommand`'s error and checking for `BucketAlreadyOwnedByYou`/`BucketAlreadyExists`, treating either as success. Added `packages/storage/test/index.test.ts` (this package had zero tests before this batch) covering: basic create-then-no-op-on-recall, a *different* client instance calling `ensureBucket()` against a bucket another instance already created (the actual race shape), and five genuinely concurrent `ensureBucket()` calls via `Promise.all` against a brand-new bucket. Verified these tests actually discriminate by reverting the fix and confirming the "different client instance" and "concurrent calls" tests both fail with the exact `BucketAlreadyOwnedByYou` error the real Docker run produced — not a different, weaker failure mode.

A second, much smaller bug surfaced while writing that test suite: the initial bucket names (`ironside-storage-test-concurrent-<full-uuid>`) exceeded S3's 63-character bucket name limit, causing an `InvalidBucketName` error unrelated to the thing being tested. Fixed by using a short random suffix instead of a full UUID — a reminder that test fixtures need the same scrutiny as production code.

## License

`LICENSE.md` — an Ironside-adapted version of coeval's (same author) Sustainable Use License v1.0, per the original planning doc's stated intent ("monetization mirrors coeval: sustainable-use license, paid hosted cloud + enterprise self-host features later"). The one meaningful adaptation from coeval's wording: coeval's "Use" clause restricts free use to "internal business purposes or non-commercial/personal use," while Ironside's explicitly permits commercial self-hosting for your own organization outright — self-hosting your own trace storage is the core value proposition this product exists to deliver, not an edge case to gate behind a stricter clause than necessary. The "Competing Use" clause is the actual restriction: you can't offer Ironside to third parties on a hosted/managed basis or embed it in a product you sell, without a separate commercial agreement — self-hosting for your own org's own use is explicitly carved out as not a competing use, since a naive reading of "no hosted or managed basis" could otherwise be misread as prohibiting the exact self-hosting this whole batch just built support for.

`package.json`'s `"license": "SEE LICENSE IN LICENSE.md"` field already existed (from M0's scaffold, matching coeval's convention) but pointed at a file that had never been created — confirmed by checking before writing anything.

## CI release workflow

`.github/workflows/release.yml`, triggered on `v*.*.*` tag pushes (not on every push/PR — that's `ci.yml`'s job, which already runs build/typecheck/test on every commit). Builds all three images via a matrix job and pushes to `ghcr.io/<owner>/ironside-{api,worker,web}:<version>` plus a rolling `:latest` tag. Uses `docker/build-push-action`'s GitHub Actions cache (`type=gha`) so incremental releases don't rebuild every layer from scratch. No test re-run in this workflow — a tag is only pushed after `ci.yml` has already gone green on that commit, so re-testing here would be redundant, not additional safety.

## Code review findings — one real bug, one false-positive claim disproven by testing, one doc-accuracy fix

Code review flagged `@ironside/mappers` (imported at the top of `apps/api/src/routes/traces.ts`, used by `GET /api/v1/traces/:id`) being listed under `devDependencies` rather than `dependencies` in `apps/api/package.json`, claiming the runtime image's `pnpm install --frozen-lockfile --prod` step would skip it and crash the api container at boot. **This claim did not reproduce**: built the actual image and ran it standalone against the real dev network, and it started and served `GET /api/v1/traces/:id` correctly. Investigated why — pnpm's workspace-protocol (`workspace:*`) dependencies are symlinked into the consuming package's own `node_modules` (e.g. `apps/api/node_modules/@ironside/mappers → ../../../packages/mappers`) as part of resolving the *workspace graph*, which is a structural step independent of the `--prod` flag; `--prod` only skips regular npm-registry devDependencies, not workspace links. Confirmed directly (`docker exec ... ls apps/api/node_modules/@ironside/`) that the symlink existed even under `--prod`, and confirmed Node's ESM resolution finds it correctly.

Moved `@ironside/mappers` to `dependencies` anyway — it's semantically accurate (it IS a runtime dependency, not a dev-only one) and removes reliance on an implementation detail of pnpm's workspace linking that isn't guaranteed to hold across pnpm versions/configurations, even though it currently isn't the crash the reviewer described. This is a case where taking a review finding seriously enough to verify it empirically — rather than either blindly implementing the suggested fix or dismissing the claim outright — produced the right outcome: the claimed *symptom* was wrong, but the underlying *smell* (a runtime-imported package classified as dev-only) was real and worth fixing regardless.

Moving the dependency required regenerating `pnpm-lock.yaml` (`pnpm install`, no version changes, just re-deriving the dependencies/devDependencies split) — caught by a subsequent fresh Docker build failing with `ERR_PNPM_OUTDATED_LOCKFILE` under `--frozen-lockfile`, a useful confirmation that the Dockerfile's `--frozen-lockfile` flag is doing its job (refusing to silently diverge from the committed lockfile) rather than an unrelated problem.

Also fixed a genuine doc-accuracy issue: `docs/self-hosting.md` claimed `http://localhost:8080/api/...` covered "any OTLP/LangFuse-compatible client," but OTLP is mounted at `/v1/otel/traces` (top-level, not under `/api/`, matching OTel exporter conventions — see `apps/api/src/app.ts`'s own comment on this), which `apps/web/nginx.conf` didn't proxy. Rather than just correct the doc's wording, added a `/v1/` proxy location to `nginx.conf` so the documented convenience is actually true (verified live: `POST http://localhost:8080/v1/otel/traces` returns `200`) — the SPA has no client-side routes under `/v1`, so this can't collide with `react-router`.

**A separate, unrelated bug surfaced while re-verifying**: `packages/clickhouse/test/retention.test.ts`'s new grace-period test (added to prove the TOCTOU-race fix) was flaky under `pnpm test`'s default cross-file parallelism — passed consistently in isolation, failed intermittently in the full suite. Root-caused (not just retried until green) via `vitest run ... --no-file-parallelism`, which passed consistently, proving genuine cross-file interference: the test's original fixture used a "5 years ago" timestamp, which — since ClickHouse partitions aren't test-scoped or project-scoped, and multiple test *files* share one live ClickHouse instance and run concurrently by Vitest's default — is legitimately droppable data from the point of view of `apps/worker/test/retention-runner.test.ts`'s own concurrently-running retention calls (cutoffs of up to 365 days, all far more permissive than 5 years). Fixed by changing the fixture to a timestamp within the *current* month's partition (2 hours ago, not 5 years), which no other test's retention cutoff would ever legitimately consider droppable — verified via 3 consecutive full-suite runs with default parallelism, all green.
